## Architecture

Standard Spring Boot layered architecture: `controller` → `service` → `repository` → `model`, with DTOs for API contracts.

**Package root:** `it.iacovelli.nexabudgetbe`

**18 controllers:** Auth, User, Account, Transaction, Category, Budget, CryptoPortfolio, Gocardless (deprecated shim), Banking, Trash, Report, BudgetTemplate, BudgetAlert, AuditLog, ApiKey, Import

**Key patterns:**
- All entities use UUID primary keys (`@GeneratedValue(strategy = GenerationType.UUID)`)
- Lombok used throughout for boilerplate
- Caching via Spring Cache + Valkey/Redis (6h TTL for most caches; 5m for crypto prices)
- JWT stateless auth — `JwtAuthenticationFilter` → `JwtTokenProvider`

## Security & Validation Behaviours

- **Password update** must always go through `UserService.updateUserProfile()` — never set `passwordHash` directly on the entity (bypasses BCrypt). `updateUserProfile()` also rejects a username/email already used by another user (`IllegalStateException` → 409).
- **JWT user lookup**: `JwtAuthenticationFilter` resolves the user from the token `sub` (user id, via `JwtTokenProvider.getUserIdFromJWT()` + `UserDetailsServiceImpl.loadUserById()`), **never** from the `username` claim: usernames are mutable, so a still-valid token would otherwise authenticate as whoever later takes that username.
- **Budget ownership**: `updateBudget` and `deleteBudget` in `BudgetController` use `getBudgetByIdAndUser()` — only the owning user can modify a budget.
- **Category uniqueness**: `CategoryService.createCategory()` and `renameCategory()` check `existsByUserAndName()` before saving and throw `IllegalStateException` (409) on duplicate. Categories are no longer tied to a `TransactionType`.
- **Default categories are read-only**: `CategoryRepository.findByIdAndUser()` also matches default categories (`user IS NULL`) — fine for *reading/assigning* (budgets, transactions), never for *modifying*. Rename/delete use `getOwnedCategoryByIdAndUser()` (`findOwnedByIdAndUser`, `c.user = :user` only) → 404 on a default category. Deleting a category still referenced by transactions/budgets/templates returns 409 (merge it instead). Budget create/update resolve the category with `getCategoryByIdAndUser()` (own or default), never `getCategoryById()` (any user's).
- **Budget date validation**: `BudgetService.validateBudgetDates()` is called by both `createBudget()` and `updateBudget()` — throws `IllegalArgumentException` if `endDate < startDate`.
- **Bank sync lock (both providers)**: `AccountService.tryAcquireSyncLock()` issues an atomic `UPDATE … SET isSynchronizing = true, syncStartedAt = now WHERE isSynchronizing = false OR syncStartedAt IS NULL OR syncStartedAt < now − SYNC_LOCK_TIMEOUT` via `AccountRepository.markSynchronizing()` — avoids reading and writing the flag in two separate round trips, and a lock orphaned by a crash/redeploy mid-sync (no `finally`) expires after `SYNC_LOCK_TIMEOUT` (1h) instead of blocking the account forever. Locks without timestamp (taken before `sync_started_at` existed) count as orphaned. Release and outcome are **targeted updates** (`releaseSyncLock`, `markSyncCompleted`, `markRequiresReauth`), never `save(account)`: a sync can last minutes and saving the entity loaded at its start would overwrite concurrent changes (rename, re-link). Migration `db/V14__add_sync_started_at_to_accounts.sql` (manual in prod).
- **GoCardless token**: `GocardlessService.generateBankLinkForToken()` returns `Optional<GocardlessCreateWebToken>` — callers must handle `Optional.empty()` (controller throws `503`).
- **Multi-provider bank aggregation**: `Account.provider` (new `BankProvider` enum: `GOCARDLESS`/`ENABLE_BANKING`, nullable — null means never linked/manual account) discriminates which strategy owns a conto. `service/bank/BankAggregationProvider` is the provider-agnostic interface (`getInstitutions`, `startLink`, `completeLink`, `getProviderAccounts`, `fetchTransactions`), implemented by `GocardlessAggregationProvider` (thin adapter over the unchanged `GocardlessService`) and `EnableBankingAggregationProvider` (wraps `EnableBankingService`). `AccountService` holds a `Map<BankProvider, BankAggregationProvider>` built from all registered beans and dispatches on `account.getProvider()` via `resolveProvider()`. Both `requisitionId` and `externalAccountId` on `Account` are generic, provider-agnostic columns reused across providers (GoCardless requisitionId/account id, Enable Banking session_id/account uid). `AccountService.syncAccountTransactions()` is the provider-agnostic sync entrypoint (lock/6h-guard/balance-alignment logic unchanged); `syncAccountTransactionWithGocardless()` / `linkAccountToGocardless()` remain as `@Deprecated` thin aliases for compat. Transaction dedup on import uses `TransactionRepository.findByExternalIdAndAccount()` (scoped to the account, not global) to avoid externalId collisions across providers. New unified endpoints: `GET/POST /api/banking/{provider}/...` (`provider` = `gocardless` | `enable-banking`) in `BankingController`; the legacy `/api/gocardless/**` (`GocardlessController`) is kept as a `@Deprecated` shim, unchanged, for frontend compat.
- **Enable Banking specifics**: unlike GoCardless (fronted by an external `gocardless-integrator` microservice), `EnableBankingService` calls `api.enablebanking.com` directly. Auth is a per-request `Authorization: Bearer <JWT>` — RS256, signed in-app with the `ENABLEBANKING_PRIVATE_KEY` (PKCS8 PEM; literal `\n` in the env var are normalized to real newlines before parsing), cached in memory until shortly before expiry (`kid` header = `ENABLEBANKING_APP_ID`). The `aud` claim must be emitted as a plain string (`.audience().single(...)`, not `.add(...)` which produces an array) — Enable Banking rejects the array form with `401 "JWT audience is not valid"`. Link flow has an extra step versus GoCardless: `startLink()` opens the bank consent redirect (no `providerReference` yet); `completeLink()` exchanges the callback `code` for a session (`session_id` → persisted on `Account.requisitionId`) plus the authorized accounts. `getTransactions()` paginates via `continuation_key` (capped at `MAX_TRANSACTION_PAGES=50`, logs a warning if the cap is hit — no silent truncation). A 401/403 from `/accounts/{uid}/transactions` is translated into `BankReauthRequiredException` (parent of `GocardlessRequisitionExpiredException`, so `AccountService`'s catch block handles both providers uniformly) via the same Spring Retry `@Recover` gotcha as GoCardless (see below) — a dedicated `@Recover(BankReauthRequiredException, ...)` just rethrows. **`EnableBankingAggregationProvider.getInstitutions()` encodes `institutionId` as `"<aspspName>|<country>"`** since Enable Banking identifies an ASPSP by name+country, not a single id like GoCardless — `startLink()` splits on `|`; the frontend must pass the `id` back verbatim, not reconstruct it. `maximum_consent_validity` from `/aspsps` is in **seconds**: `toInstitutionDto()` converts it to days for `maxAccessValidForDays`, and `startLink()` caps `ENABLEBANKING_CONSENT_VALID_DAYS` to that maximum (looked up in the cached ASPSP list). A session with zero accounts (typical of a production app still pending/restricted, where only control-panel-whitelisted accounts are returned) is logged as a warning in `completeLink()`. **Optional provider, graceful fallback**: `EnableBankingService.init()` (`@PostConstruct`) never throws — if `ENABLEBANKING_APP_ID`/`ENABLEBANKING_PRIVATE_KEY` are blank or the key fails to parse, it logs a warning and sets `configured=false` instead of failing application startup (GoCardless-only deployments are unaffected). `isConfigured()` exposes this flag. `EnableBankingAggregationProvider.requireConfigured()` is the single choke point checked at the top of all 5 `BankAggregationProvider` methods — when unconfigured it throws `ResponseStatusException(503, ...)`, which `BankingController`'s `/api/banking/enable-banking/...` endpoints surface directly via the existing `GlobalExceptionHandler` (no per-endpoint handling needed). `EnableBankingService.currentToken()` also has a defensive `configured` guard as defense-in-depth, but it should be unreachable in practice since the provider-level check runs first. Full setup walkthrough (control panel registration, RSA key generation, troubleshooting the 401/422 pitfalls above): `docs/ENABLE_BANKING_SETUP.md`.
- **Bank sync dedup (booked only + auto-reconcile)**: both providers import **only booked transactions** — `GocardlessService.extractBookedTransactions()` reads `transactions.booked` (falls back to `all` with a warning only if the integrator omits `booked`); `EnableBankingAggregationProvider.fetchTransactions()` drops rows with `status != BOOK` (null status = booked). Pending rows used to get a provisional/absent id that changed on booking, producing duplicates. `externalId` resolution: GoCardless `transactionId` → `internalTransactionId`; Enable Banking `entry_reference` → `transaction_id`; then `BankTransactionIds.ensureExternalIds()` fills any remaining null with a deterministic `"nxb:" + SHA-256(accountId|date|amount|descriptive fields)#occurrence` — never query dedup with a null externalId (it would match manual rows via `IS NULL`). `TransactionService.importNormalizedTransactions()` dedups via native `countByAccountIdAndExternalIdIncludingDeleted()` (ignores `@SQLRestriction`, so soft-deleted bank rows are **not** re-imported) and swallows `DataIntegrityViolationException` per row. After import, `AccountService.syncAccountTransactions()` calls `BankDuplicateReconciliationService.reconcile(account, booked)` (errors logged, never fail the sync; runs before balance alignment): soft-deletes (recoverable from trash) (1) rows sharing the same `externalId` on the account — keeps categorized, then oldest; (2) orphan pending rows — externalId not among the received booked ids, not a transfer, not a file import (`importHash` null), date within `[minBookedDate+5d, today-10d]`, matching a booked row with same type+amount within ±5 days that was created **after** it. Category/note are moved to the survivor if it has none. **Effetti da conoscere**: (a) se un conto cambia provider (GoCardless → Enable Banking) tutte le righe del vecchio provider risultano orfane e vengono rimosse quando matchano una riga del nuovo provider (stesso tipo+importo ±5gg) — comportamento voluto (elimina i doppioni del re-link), categoria/nota migrano; (b) le righe bancarie importate prima di questo cambio con `external_id NULL` non sono distinguibili dalle manuali, quindi il riallineamento non le tocca e al primo sync possono comparire una volta come duplicati (ora ricevono `internalTransactionId`/hash `nxb:`) — vanno ripulite a mano dal cestino/UI. Migration `db/V13__unique_external_id_per_account.sql` (manual in prod): moves same-`(account_id, external_id)` extras to trash with `external_id=NULL`, then creates partial unique index `uk_transaction_account_external_id ON transactions(account_id, external_id) WHERE external_id IS NOT NULL`.
- **Category merge**: `CategoryService.mergeCategories(sourceId, targetId, user)` moves transactions (native `updateCategoryBulkIncludingDeleted` — **includes soft-deleted rows**, otherwise trashed transactions keep the FK and block the delete), budgets and budget templates to the target, then deletes the source category — all in one `@Transactional`. Source must be user-owned (not a default category). No `TransactionType` constraint. Any new entity referencing `Category` must be added to the merge.
- **Soft delete**: `Transaction` and `Account` use `@SQLRestriction("deleted = false")`. DELETE endpoints now soft-delete (set `deleted=true, deleted_at=now`). Hard delete never happens via normal endpoints. All `@Modifying` native queries use `clearAutomatically = true, flushAutomatically = true` to keep the Hibernate L1 cache consistent. `TransactionRepository.hardDeleteAll()` and `AccountRepository.hardDeleteAll()` exist for test teardown only.
- **Trash recovery**: `GET /api/trash/transactions`, `GET /api/trash/accounts`, `POST /api/trash/{type}/{id}/restore`. `TrashService.purgeExpiredItems()` hard-deletes items older than 30 days (cron `0 0 3 * * ?`); the transaction purge also removes all transactions of expired accounts (otherwise the `transactions.account_id` FK fails the account purge and rolls back the whole job). Restore semantics: restoring one leg of a transfer restores **both** legs (`restoreByTransferIdAndUserId`); restoring a transaction whose account is in the trash → 409 (restore the account first); restoring an account restores **only** the transactions deleted together with it — `AccountService.deleteAccount()` uses one timestamp for account and transactions, and `restoreAccount()` restores rows with `deleted_at` in `[account.deletedAt − 5s, account.deletedAt + 1s]` (the window covers accounts deleted before the shared timestamp), so rows trashed earlier (e.g. duplicates removed by bank reconciliation) stay in the trash.
- **Scheduling**: `@EnableScheduling` is on `AsyncConfig`. Budget template instantiation runs at `0 0 1 1 * ?` (1 AM on 1st of month). Budget alert checks run every hour (`fixedRate = 3_600_000`). Trash purge runs at `0 0 3 * * ?`.
- **Budget templates**: `BudgetTemplate` entity with `RecurrenceType` (MONTHLY/QUARTERLY/YEARLY). `createTemplate()` and `updateTemplate()` always set `startDate = first day of current month` via `upsertCurrentPeriodBudget()` — if an active budget already exists for that user+category it is updated in-place, otherwise a new one is created. The cron job `instantiateTemplates()` at `0 0 1 1 * ?` handles future months and skips templates whose user+category already has an active budget. QUARTERLY periods end at the end of the **calendar** quarter (a template created in February gets Feb 1 – Mar 31), so they never overlap the quarter the cron creates in Jan/Apr/Jul/Oct. Overlapping budgets are still possible (manual budget + template, category merge): `BudgetRepository.findActiveBudgetByUserAndCategoryAndDate()` is a `default` method returning the most recent one (`ORDER BY startDate DESC`) — never turn it back into a single-result `Optional` query (it threw `IncorrectResultSizeDataAccessException` and broke the hourly alert job). `POST/GET/PUT/DELETE /api/budget-templates`.
- **Budget alerts**: `BudgetAlert` entity stores per-budget threshold (1–100%). Scheduler checks hourly. Notification is sent **once per budget period**: the cooldown check compares `lastNotifiedAt` against `budget.startDate` (not a fixed 24h window) — if `lastNotifiedAt >= startDate` the alert is already consumed for that period. `POST/GET/PUT/DELETE /api/budget-alerts`. Email HTML via `EmailService` (async). Logs prefixed `[BudgetAlert]` trace every step: alerts found, budget missing, usage %, threshold crossed, cooldown active.
- **Budget monthly summary (dashboard)**: `GET /api/budgets/monthly-summary?date=` returns `List<BudgetDto.MonthlySummaryResponse>` — one row per active budget for the reference month. Each row includes `budgetId`, `categoryId`, `categoryName`, `limit`, `spent` (net OUT−IN for that category in the month), `remaining`, `percentageUsed`, `budgetStartDate`, `budgetEndDate`, `periodStart`, `periodEnd`. Reuses `BudgetService.getBudgetUsage()` (backed by `TransactionRepository.sumNetByUserAndCategoryAndDateRange()`). `spent` can be negative when refunds exceed expenses. Designed for the dashboard budget table widget.
- **Financial reports**: `ReportService` uses JPQL `GROUP BY YEAR/MONTH` aggregate queries. Endpoints: `GET /api/reports/monthly-trend?months=12`, `/category-breakdown?startDate=&endDate=` (net breakdown), `/month-comparison?year=&month=`, `/monthly-projection`. **Semantica critica — tutti i report sono sul netto per categoria**: `category-breakdown`, `monthly-trend`, `month-comparison` e `monthly-projection` usano il **netto per categoria** (`SUM(OUT) − SUM(IN)` per categoria, via `findCategoryNetBreakdown` + `findUncategorizedTotalsByType`, aggregati da `ReportService.aggregateNetTotals()`/`buildMonthlyNetMap()`): una categoria con netto positivo conta come spesa, una con netto negativo come entrata; le transazioni senza categoria contano per tipo (lordo). Un rimborso nella stessa categoria di una spesa la riduce invece di gonfiare le entrate. I trasferimenti (`transferId` non null) sono esclusi ovunque. Non introdurre nuovi report sul lordo (`sumByUserAndTypeAndDateRangePerCurrency`) senza documentarlo: i totali non sarebbero confrontabili. `CategoryBreakdownResponse` espone `totalExpense` (somma net delle righe OUT) e `totalIncome` (somma net delle righe IN) — la somma delle `CategoryBreakdownItem.net` con `inferredType=OUT` è sempre uguale a `totalExpense`; usare questi campi come "spesa/entrata totale" nella vista breakdown, non i totali di altri endpoint. `grandTotal` è deprecato (valorizzato uguale a `totalExpense` per retro-compatibilità). Categorie con `net=0` (spese interamente rimborsate) compaiono nell'elenco con `percentage=0` e `inferredType=OUT`. `CategoryBreakdownItem` has `net` (absolute value of net), `percentage` (% within its group), `inferredType` (OUT if net≥0, IN if net<0). Nuova implementazione AI Asincrona tramite polling con timeout rate-limite a 1 Anno su endpoint in `AiReportService` (salvata in Valkey cache temporanea): `POST /api/reports/ai-analysis` e `GET /api/reports/ai-analysis/{jobId}`. Nessun CSV allegato: il modello recupera aggregati e singole transazioni del periodo via tool calling (`FinanceTools`, es. `getTransactionsInPeriod`). Se `nexabudget.ai.report.self-review.enabled` (default `true`) una seconda chiamata, anch'essa con i tool, rivede la bozza (coerenza numerica, 4 sezioni obbligatorie) — raddoppia costo/latenza; se fallisce si usa la bozza. Ogni chiamata (bozza e self-review) che fallisce o restituisce testo vuoto viene ripetuta una volta con `nexabudget.ai.report.fallback-model` (`NEXABUDGET_REPORT_FALLBACK_MODEL`, default `gemini-2.5-flash`; vuoto o uguale al primario = nessun fallback). La chiamata è asincrona con generazione stato pending.
- **Report AI in cache**: `AiReportService.startAiReportJob()` restituisce lo stato iniziale del job (non va riletto dalla cache subito dopo averlo scritto: in ambiente la rilettura immediata ha restituito null → 400 "Job non trovato o scaduto" sulla POST). Se l'ha già risolto dalla cache risultati (`COMPLETED`) `ReportController.startAiReport()` lo restituisce subito senza chiamare `generateAiReport()` (che ripagherebbe le chiamate AI e rimanderebbe l'email). `getJobStatus()` nega l'accesso se l'owner del job manca in cache. **Job orfani (restart del pod)**: mentre `generateAiReport()` gira, un task del `TaskScheduler` aggiorna `heartbeat_<jobId>` in `AI_REPORTS_CACHE` ogni `HEARTBEAT_INTERVAL` (30s; scritto anche da `startAiReportJob()` prima dello stato PENDING); `getJobStatus()` dichiara `FAILED` (e lo salva) un job `PENDING` con heartbeat assente o più vecchio di `HEARTBEAT_STALE_AFTER` (3 min) — altrimenti un pod morto a metà generazione lascerebbe il job PENDING per sempre. Il job non viene rilanciato in automatico: l'utente riprova (eviterebbe doppie chiamate AI/email).
- **AI chat/report (Spring AI `ChatClient`)**: NexaBot (`ChatService`, `/api/chat`) e il report AI (`AiReportService`) usano il `ChatClient` di Spring AI costruito a mano in `AiChatClientConfig` (Spring AI 2.0.x non ha autoconfig per il chat model Google GenAI) sopra il `Client` di `GenAiSdkConfig`. Modello/temperatura/thinking sono per-chiamata via `GenAiChatOptionsFactory.build()` (Gemma 4 → `thinkingLevel`, Gemini → `thinkingBudget`; un thinking level non valido viene loggato e ignorato invece di far fallire la chiamata). I tool sono i metodi `@Tool` di `FinanceTools`, passati come `TrackedToolCallbacks` (un'istanza per richiesta): il loop interno di Spring AI non espone i tool eseguiti né ha un tetto, quindi il wrapper registra i nomi (→ `ChatResponse.toolsUsed` e messaggi `TOOL` salvati) e oltre `MAX_TOOL_CALLS` (chat 15, report 25 per chiamata) smette di eseguire tool e chiede al modello di rispondere con i dati raccolti. I tool leggono l'utente da `SecurityContextHolder`: il report, che gira `@Async`, imposta il contesto a mano. Il `Client` GenAI (`GenAiSdkConfig`) ha un timeout per singolo tentativo HTTP (`nexabudget.ai.http-timeout-seconds`, default 120; l'SDK ritenta fino a 5 volte con backoff, quindi il caso peggiore per un turno è di diversi minuti, ma limitato): di default l'SDK usa timeout 0 = infinito, e una chiamata appesa lasciava il job del report `PENDING` per sempre, senza log né email e senza far scattare il fallback.
- **Chat transactions & history**: `ChatService.chat()` is deliberately **not** `@Transactional`: the model call (tens of seconds, with tools) runs outside any transaction, so it doesn't hold a pool connection and a failing tool (which opens its own transaction) can't mark the whole chat rollback-only (→ `UnexpectedRollbackException`/500). Three phases via `TransactionTemplate` (a `@Transactional` helper in the same class would bypass the proxy): (1) short read-only tx — session ownership check (404 before calling the model) + history; (2) model call; (3) short write tx — `persistExchange()` re-loads the session (or creates it if new) and saves USER message, ASSISTANT reply, `TOOL` rows and title together. **If the model call fails nothing is persisted** (no user message, no fallback reply, no new session): `callWithTools()` flags the `ChatResult` as `failed` and `chat()` returns the fallback text with the requested `sessionId` (null for a new session) without opening the write transaction. History is read **before** the new USER message is saved (`callWithTools()` already sends it as the last user turn); `findLastNBySessionId` excludes `TOOL` rows so they don't consume the history window. Don't add `@Transactional` back to `chat()`.
- **Email Notifications**: `EmailService` gestisce l'invio di email SMTP. In dev usa Mailhog (localhost:1025). Le email usano template HTML inline. Errori nell'invio vengono loggati ma non bloccano i processi chiamanti.
- **Multi-currency transfers**: `TransactionService.createTransfer()` e le funzioni di conversione (`convertTransactionToTransfer`) detects when source/destination account currencies differ, calls `ExchangeRateService.getRate()`, converts the amount, and stores `exchangeRate`, `originalCurrency`, `originalAmount` on the IN transaction (invariant: IN.amount = OUT.amount × exchangeRate). `convertTransactionsToTransfer()` (two existing rows) keeps both real amounts when currencies differ and derives `exchangeRate = IN/OUT`; only same-currency pairs are normalized to the first amount. `updateTransaction()` on a transfer leg recomputes the other leg via `syncTransferLegAmounts()` using the stored rate (never copies the amount across currencies) and sets the other leg's type to the opposite of the edited one. `AccountService.getTotalConvertedBalance()` aggregates the user's balances by converting via `CurrencyConversionService` to the user's `defaultCurrency`.
- **Error mapping (`GlobalExceptionHandler`)**: `IllegalArgumentException`/malformed JSON/type mismatch (e.g. non-UUID path variable)/missing param → 400; `AccessDeniedException` → 403; `NoResourceFoundException` → 404; wrong HTTP method → 405; `IllegalStateException`/`DataIntegrityViolationException` → 409; everything else → 500. Prefer throwing these over letting client errors reach the catch-all.
- **Audit log**: `AuditAspect` (`@Aspect @Component` in `config/`) intercepts service write methods via `@AfterReturning` and records to the `audit_logs` table via `AuditLogService`. User resolved from `SecurityContextHolder`; IP from `RequestContextHolder` (first `X-Forwarded-For` value, truncated to the 64-char column: the audit INSERT runs at the caller's commit, so an oversized value would fail the business operation itself). Endpoints: `GET /api/audit-log?page=0&size=20`, `GET /api/audit-log/{entityType}/{entityId}`.
- **API Key auth**: `ApiKey` entity stores SHA-256 hash of the plaintext key (never stored plain). `ApiKeyAuthenticationFilter` reads `X-Api-Key` header, hashes it, looks up in DB, validates active + not expired, updates `lastUsedAt`. Filter runs before `JwtAuthenticationFilter`. Dual auth: JWT session OR API key. Endpoints: `POST/GET/PUT/DELETE /api/api-keys`. Key shown in plaintext **only** at creation. API-key requests are authenticated with `ApiKeyAuthenticationToken` (distinct from the JWT `UsernamePasswordAuthenticationToken`): `ApiKeyAuthenticationToken.isCurrentRequestApiKeyAuthenticated()` is checked by `ApiKeyController.createApiKey()` (an API key cannot mint new keys) and `UserController.updateUser()` (an API key cannot change email or password) → 403. `scopes` are stored but not otherwise enforced.
- **Import CSV/OFX**: `ImportService` parses CSV (via Apache Commons CSV + configurable `CsvColumnMapping`) and OFX 1.x SGML / 2.x XML (regex-based). Deduplication via SHA-256 hash of `(accountId|date|amount|description)` stored in `transactions.import_hash`; identical rows within the same file get an occurrence suffix (`#1`, `#2`, …; the first occurrence keeps the historic hash) so legitimate repeated payments are not collapsed. FITID dedup uses `countByAccountIdAndExternalIdIncludingDeleted()` — scoped to the account and including soft-deleted rows, consistent with the `uk_transaction_account_external_id` unique index. CSV amounts go through `ImportService.normalizeAmount()` (handles thousands separators: "1.234,56" / "1,234.56"; if both separators are present the last one is decimal). A CSV type column is IN only for exactly `IN` or values containing `CREDIT`/`ENTRATA`/`ACCREDITO`. `selectedHashes` null **or empty** = import all non-duplicates. AI auto-categorizes imported rows. Two-step flow: preview (`/csv/preview`, `/ofx/preview`) then confirm (`/csv`, `/ofx`). Endpoints under `POST /api/accounts/{id}/import/…`.

## Resilience & Performance

- **Spring Retry** (`spring-retry:2.0.13` + `aspectjweaver:1.9.25.1`): `@EnableRetry` is on `AsyncConfig`. `@Retryable(retryFor = RestClientException.class, maxAttempts = 3, backoff = @Backoff(delay = 1000, multiplier = 2))` applied to all `GocardlessService` and `EnableBankingService` public methods, and `ExchangeRateService.getRate()`. Cached methods use `unless` conditions to prevent caching empty fallback results (which would block retries on subsequent calls).
- **HTTP timeouts**: GoCardless 5 s connect / 10 s read; Enable Banking 5 s connect / 10 s read; Binance 5 s / 5 s; ExchangeRate 5 s / 5 s.
- **Crypto portfolio cache**: `getPortfolioValue()` is cached per user **and currency** (`#user.id + '_' + currency`), TTL 5m like crypto prices; the write methods evict with `allEntries = true` since they don't know which currencies are cached. Unit prices are converted with scale 8 (`convertFromUsd(price, currency, 8)`) — scale 2 zeroes sub-cent tokens. Manual holdings are looked up with the upper-cased symbol. `CoinbaseService.getWallets()` throws if both the accounts and the portfolios scan fail (an empty list would make `syncCoinbaseHoldings()` delete all Coinbase holdings).
- **Batch crypto prices**: `BinanceService.getAllTickerPricesUsdt()` fetches all prices in a single API call and is used by `CryptoPortfolioService.getPortfolioValue()`. Per-symbol `getTickerPrice()` is used only as fallback for symbols not present in the batch map.
- **Cache warming**: `CacheWarmupRunner` pre-populates exchange rate cache (USD → EUR/GBP) at startup via `CompletableFuture.runAsync()`.

## Key Architecture Notes

- **`BudgetService`** depends directly on `TransactionRepository` (not `TransactionService`) for the net aggregation query `sumNetByUserAndCategoryAndDateRange()`. `getBudgetUsage()` and `getRemainingBudgets()` are `@Transactional(readOnly = true)` to keep the Hibernate session open across lazy-loaded associations.
- **Net category accounting**: `Category` no longer has a `transactionType` field. Budget spent = OUT−IN on the same category within the period. `GET /api/categories/type/{type}` endpoint has been removed (breaking change). DB migration required: `ALTER TABLE categories DROP CONSTRAINT uk_category_user_name_type; ALTER TABLE categories DROP COLUMN transaction_type; ALTER TABLE categories ADD CONSTRAINT uk_category_user_name UNIQUE (user_id, name);`. Before dropping, deduplicate rows with the same `name` per user: remap `transactions.category_id` / `budgets.category_id` to the surviving row, then delete duplicates.
- **Transaction pagination**: `GET /api/transactions/paged?page=0&size=20` returns `Page<TransactionResponse>`. The underlying `findByUserPaged()` uses a split count query to avoid HQL pagination issues with `JOIN FETCH`.
- **DB indexes** are declared via `@Index` on `Transaction` (`user_id+transaction_date`, `account_id+transaction_date`, `category_id`) and `Budget` (`user_id+start_date+end_date`). DDL mode is `validate` in production — new indexes require a separate DB migration script.
- **New DB columns** added by Phase 4: `transactions.deleted` (BOOLEAN NOT NULL DEFAULT false), `transactions.deleted_at` (TIMESTAMP), `accounts.deleted` (BOOLEAN NOT NULL DEFAULT false), `accounts.deleted_at` (TIMESTAMP). New tables: `budget_templates`, `budget_alerts`. These must be migrated manually in production.
- **New DB columns** added by Phase 5: `transactions.exchange_rate` (DECIMAL(20,8)), `transactions.original_currency` (VARCHAR(3)), `transactions.original_amount` (DECIMAL(19,4)), `transactions.import_hash` (VARCHAR(64)). New tables: `audit_logs`, `api_keys`. These must be migrated manually in production.
- **New DB column** added by Phase 6: `accounts.requires_reauth` (BOOLEAN NOT NULL DEFAULT false). Must be migrated manually in production.
- **New DB column** (Enable Banking integration, `db/V12__add_bank_provider_to_accounts.sql`): `accounts.provider` (VARCHAR(32), nullable). Backfills existing GoCardless-linked rows (`requisition_id`/`external_account_id` not null) to `'GOCARDLESS'`. Must be migrated manually in production (`ddl-auto=validate`).
- **New DB column** (expiring bank sync lock, `db/V14__add_sync_started_at_to_accounts.sql`): `accounts.sync_started_at` (TIMESTAMP, nullable). Must be migrated manually in production (`ddl-auto=validate`).
- **Bank fetch failures are not empty syncs**: the transaction-fetch `@Recover` methods (`GocardlessService.recoverGetGoCardlessTransaction`, `EnableBankingService.recoverGetTransactions`) **throw** after retries are exhausted instead of returning an empty list — an empty list would be treated as a successful sync (fake "Allineamento conto" row, `lastExternalSync` advanced, Enable Banking rows of the gap never fetched again). `syncAccountTransactions()` requests from `lastExternalSync − SYNC_OVERLAP_DAYS` (7) to catch late-booked rows (externalId dedup absorbs the overlap); providers whose fetch honours `startDate` (`BankAggregationProvider.supportsIncrementalFetch()`, true for Enable Banking) pass it to `BankDuplicateReconciliationService.reconcile(account, booked, requestedFrom)` so stored rows before the requested window are not treated as orphans. The Enable Banking transactions cache key includes `dateFrom`. Switching an account to a different provider (`addRequisitionIdToAccount`) clears the old `externalAccountId`; a sync on an account without `externalAccountId` sets `requiresReauth=true` instead of calling the provider.
- **GoCardless requisition expired during transaction sync**: `GocardlessService.getGoCardlessTransaction()` inspects `data.error_code`/`data.requisitionStatus` on the integrator response (mapped onto `GocardlessBankTransaction`) and throws `GocardlessRequisitionExpiredException` (e.g. `ITEM_LOGIN_REQUIRED` / `requisitionStatus=EX`) instead of silently returning an empty transaction list. `AccountService.syncAccountTransactionWithGocardless()` catches it, sets `account.requiresReauth=true` and clears it back to `false` on the next successful sync; the call is inside the same `try/finally` that releases `isSynchronizing`, so the sync lock is always released even on this error. `requiresReauth` is exposed on `AccountDto.AccountResponse` — the frontend should prompt the user to call `POST /api/gocardless/bank/link` again when it is `true`. **Gotcha**: any `@Retryable` method that has at least one `@Recover` method always goes through Spring Retry's recovery lookup on the final exception, even for exception types outside `retryFor` — if no `@Recover` signature matches, it fails with `ExhaustedRetryException: Cannot locate recovery method`, masking the real exception. `getGoCardlessTransaction()` therefore needs a dedicated `@Recover(GocardlessRequisitionExpiredException, ...)` that just rethrows — add one for any new custom exception thrown from that method.
- **Schema change (net category accounting)**: `categories.transaction_type` column removed; unique constraint changed from `(user_id, name, transaction_type)` to `(user_id, name)`. Migration script: see "Net category accounting" note above.
- **`commons-csv:1.14.1`** added as a dependency for CSV import parsing.
- **`Budget` uses `@Data`** (Lombok) which generates `hashCode/equals` from all fields including lazy associations. Never use a `Budget` entity as a `HashMap` key outside a Hibernate session — iterate with `entrySet().stream().filter(e -> e.getKey().getId().equals(...))` instead.
